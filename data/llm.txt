# agenda.jurrejan.com — Dutch venue agenda feed

Concerts, club nights and festivals across the Netherlands, scraped four times
a day from three nationwide aggregators plus two dozen venues, merged into one
sorted list and published as static files. No API key, no rate limit, no
pagination. Pick the narrowest route below and read the whole file.

## Routes

The server ignores query strings, so every filter is a path. `routes.json`
lists all of them with live counts — read it first when you do not already know
the slug you want.

  /routes.json                  index of every route, with counts
  /health.json                  freshness + per-source health, ~2 KB
  /events.json  /events.tsv     everything (also /all.json, /all.tsv)
  /today.json   /week.json      next 1 / 7 days, whole country
  /month.json                   next 31 days, whole country
  /city/<slug>.json             one city, full horizon — e.g. /city/amsterdam.json
  /city/<slug>/week.json        one city, next 7 days (cities with 20+ events)
  /source/<name>.json           one scraper, e.g. /source/festivalinfo.json
  /venue/<slug>.json            one venue with 10+ upcoming events
  /artist/<slug>.json           one act with 5+ upcoming dates
  /venues.json                  every venue, with its city and event count
  /cities.json                  every city, with its event count
  /artists.json                 every extracted act, with confidence and count
  /archive/index.json           every archived month, with count and last_modified
  /archive/<yyyy-mm>.json       every event ever scraped that starts that month,
                                past ones included — e.g. /archive/2026-09.json
  /llm.txt  /llms.txt           this file

Every route exists as `.json` and `.tsv`, except the three registries and
`/archive/index.json`, which are JSON only — they hold entity records, not event rows. City, venue and
artist slugs are lowercase ASCII with dashes ("Den Haag" -> `den-haag`);
`routes.json` has the exact list.

For a small context, prefer `/city/<slug>/week.json` (tens of events) over
`/events.json` (thousands).

## Fetching

Refreshed at 04:17, 10:17, 16:17 and 22:17 Europe/Amsterdam, plus up to 10 min
jitter. `Cache-Control: max-age=900`, `Last-Modified` set, `304` on
`If-Modified-Since`, `Access-Control-Allow-Origin: *`. Do not poll faster than
every 15 minutes. Writes are atomic: a `200` is never a partial file.

## Schema

Route files share one envelope:

    {
      "schema_version": "1.1.0",                    # semver; minor = added field
      "generated_at": "2026-08-30T16:17:04+0200",   # ISO 8601, Europe/Amsterdam
      "healthy": true,                              # false = see problems
      "problems": [],
      "route": "city/amsterdam",                    # absent in events.json
      "count": 412,
      "sources": {...},                             # events.json / health.json only
      "events": [ ... ]                             # or venues / cities / artists
    }

`schema_version` is the contract this file describes. A minor bump adds a key
and never moves one; a major bump means an existing key changed meaning. Pin
nothing else: `generated_at` and the counts change four times a day.

Each event:

    date    "2026-09-12"   local start date, YYYY-MM-DD. Always present.
    end     ""             last day of a multi-day festival; "" for single-day.
    time    "20:30"        local start, HH:MM. "" when the source omits it.
    title   "Bokoesam"     as published; Dutch or English depending on source.
    venue   "Paradiso"     as published; a label, not an identifier.
    city    "Amsterdam"    Dutch spelling. "" when the source does not say.
    status  ""             "" | "Sold out" | "Waiting list" | "Cancelled" | "Postponed"
    url     "https://..."  detail/ticket page at the venue or the aggregator.
    source  "paradiso"     which scraper produced the row.

    venue_id   "paradiso"        the Venue in /venues.json. "" when no venue named.
    city_id    "amsterdam"       the City in /cities.json. "" when no city named.
    artist_ids "dixon,gizem"     comma-separated Artist ids, "" when none found.

    room       "Oude Zaal"       the room the venue label named; venue_id stays
                                 the building. "" when the label named no room.
    lat        "52.3622"         venue latitude, decimal degrees, as the source's
    lon        "4.8838"          schema.org location stated it. "" when it did not.
    address    "Weteringschans 6-8"  street address, same rule.

All sixteen keys are on every event; absence is `""`, never `null`, never a
missing key. The nine above the first gap are the original ones and keep their
order; everything after them was appended and nothing else moved. Sorted by
`(date, time, title)`. Nothing that has already finished is published — an
event with a past `date` is a festival still running, which is what `end` is
for. Finished events live on in the archive, below.

An id is the slug of the entity's canonical name, so it is stable between runs
and readable in a URL. Match on `venue_id`, not on `venue`: the same room is
spelt several ways across sources ("TivoliVredenburg", "Tivoli Vredenburg"),
and only the id collapses them.

`.tsv` is headerless, one event per line, same order, fields never containing
tabs or newlines:

    source <TAB> date <TAB> end <TAB> time <TAB> title <TAB> venue <TAB> city <TAB> status <TAB> url <TAB> venue_id <TAB> city_id <TAB> artist_ids <TAB> room <TAB> lat <TAB> lon <TAB> address

The first nine columns are the original ones, unchanged and in the original
order; the later fields were appended after them, so `cut -f2,5,7` still means
what it always meant.

## Registries

Three files name the things the events point at. They share the envelope above
and carry their records under a key matching the file name.

    /venues.json   {"id","name","city","city_id","lat","lon","address","count"}
    /cities.json   {"id","name","count"}
    /artists.json  {"id","name","confidence","count"}

A venue's `lat`, `lon` and `address` come from the first published event that
states them (JSON-LD and Partyflock's microdata do; card listings do not), and
are "" until one does.

`count` is how many currently published events belong to that entity, so the
registries are the cheap way to answer "which venue is busiest in Rotterdam"
without reading the feed. Sorted by count descending, then by name.

Artists are the soft one. No source publishes a lineup field, so the names are
lifted out of the event title by a rule: cut bracketed noise, cut a promoter's
"X presents" prefix, split on the separators promoters use (`+`, `&`, ` x `,
`b2b`, `w/`, `feat.`, `//`, `/`), then drop the parts that name a genre or a
format. `confidence` says how much that rule trusts the name:

    high    an explicit separator framed it — the strongest signal there is
    medium  the whole title was one clean name
    low     a brand prefix had to be cut off first

Filter on `confidence == "high"` when precision matters. `/artist/<slug>.json`
exists only for acts with five or more upcoming dates, which is roughly where
the false positives stop.

## Archive

The live routes drop an event once it is over; the archive never drops one.
Every run folds everything it scraped into it, finished or not, so a month
file holds the past, the present and whatever is announced ahead.

    /archive/index.json   {"months": [{"month": "2026-09", "count": 6120,
                            "last_modified": "2026-10-11T08:17:04Z",
                            "json": "/archive/2026-09.json"}, ...]}
    /archive/2026-09.json the envelope, then "events": every event whose
                          `date` falls in that month

Each archived event has every key of a live event, in the same order, plus:

    first_seen "2026-08-14T02:17:09Z"  the first run that scraped it, UTC
    last_seen  "2026-09-05T20:17:41Z"  the last run that scraped it, UTC

One row per `(venue_id, date, title)` — the same match dedupe uses, so the
venue's copy and the aggregator's are one row. Each field holds the latest
run's value, but a run that leaves a field empty never blanks one an earlier
run filled. An event that disappears before its date (cancelled, renamed,
moved) stays in the archive with an old `last_seen`; treat a `last_seen` well
before `date` as "may not have happened". A festival files under the month it
starts — check `end` for the days after.

To sync incrementally, fetch `/archive/index.json` and re-fetch only the months
whose `last_modified` moved. A month whose events are all over stops moving.
Do not rely on the HTTP `Last-Modified` header here: every month file is
rewritten on every run. Archiving began in October 2026; earlier months
hold only what an older saved snapshot could recover, so they are thin. The `.tsv` of a month route
has the live columns only, without the two timestamps.

The venue scrapers exist for what the aggregators drop: ticket status, a link
to the venue's own page, and a horizon that runs past the aggregators' 45 days.
Everything else in the country arrives through ra-nl, partyflock, podiuminfo
and festivalinfo. Belgian, German and other non-Dutch listings are filtered out
of all four.

## Health

Trust the data only when `healthy` is `true`. When it is `false`, `problems`
names each broken source: one that threw, one that returned nothing, or one
that returned less than half its recent norm (a silent parser breakage after a
site redesign). Events from the other sources in that same run are still good —
check `sources[<name>].ok`. A `generated_at` more than ~7 hours old means the
refresh timer itself stopped.

## Caveats

- Duplicates are already removed: when an aggregator and the venue itself
  report the same day + venue + title, the venue's row wins. Matching on the
  resolved venue rather than on the free-text city also catches the pair where
  only one of the two named a city. Different titles for the same night
  (promoters brand club nights differently per platform) survive as two rows —
  match loosely if exactness matters.
- Coverage differs by horizon, and this is the feed's sharpest edge. The
  aggregators are capped at 45 days (120 for festivals). The venue scrapers
  reach as far as the venue itself publishes on one page: Rotown 13 months,
  Muziekgieterij 9, dB's and De Helling 8, Musicon 5, EKKO 4. The two rendered
  ones stop where their infinite scroll stops — TivoliVredenburg ~2.5 months,
  Paradiso ~3 — and that cut-off moves between runs. So the feed is dense for
  roughly six weeks, thins out over the two months after that, and past ~4
  months only a handful of venues are represented. A quiet January is a
  coverage artefact, not an empty agenda.
- `city` and `city_id` are empty for RA events outside its six Dutch city areas.
- `artist_ids` is a guess, not a credit list. A club night branded as one word
  yields one low-confidence "artist" that is really the night; a support act
  the title never mentions is simply absent.
- `venue` is a label. RA rows carry whatever room the night is held in — a bar,
  a studio, a boat.
- `status` reflects the last scrape, up to 6 hours old, and only the venue
  scrapers set it. Confirm on `url` before telling anyone a show is sold out.

## MCP

The same feed as an MCP server — stdio, one uv command, no checkout required —
for clients that would rather call tools than fetch URLs:

    {
      "mcpServers": {
        "uitagenda": {
          "type": "stdio",
          "command": "uvx",
          "args": ["--from", "git+https://github.com/doublej/agenda-scraper",
                   "agenda-scraper", "mcp"]
        }
      }
    }

With a checkout on the same machine, point at it instead and the server reads
`data/` off the disk rather than this site — same documents either way:

    "command": "uv",
    "args": ["run", "--directory", "/home/jurrejan/development/agenda-scraper",
             "agenda-scraper", "mcp"]

Source: https://github.com/doublej/agenda-scraper. `AGENDA_DATA_DIR` and
`AGENDA_BASE_URL` override where the server looks.

    search(query, city, venue, days=14, from_date, to_date, limit=20)
        Events matching every filter given, soonest first. Words in `query` must
        all appear in the title, venue or city.
    cities()
        Every city with its event count. Call it when a city search comes back
        empty: city matching is exact on the name.
    venues(city, query, limit=30)
        Venue names as the feed spells them — what search(venue=…) matches on.

Every answer carries a `feed` block with `generated_at`, `healthy` and a `stale`
warning past 8 hours; `search` adds a `coverage` note when the window runs past
45 days.

## Recipes

    # what is on in Utrecht this week
    curl -s https://agenda.jurrejan.com/city/utrecht/week.json | jq -r '
      .events[] | "\(.date) \(.time) \(.title) — \(.venue)"'

    # every festival still to come
    curl -s https://agenda.jurrejan.com/source/festivalinfo.tsv | cut -f2,5,7

    # is the feed trustworthy right now?
    curl -s https://agenda.jurrejan.com/health.json | jq '{healthy, generated_at, count}'

    # which routes exist
    curl -s https://agenda.jurrejan.com/routes.json | jq -r '.routes[] | "\(.count)\t\(.json)"'
